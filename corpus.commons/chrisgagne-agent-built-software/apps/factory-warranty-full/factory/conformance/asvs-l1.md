## How ASVS's verification position set the statuses

ASVS says OWASP certifies no vendor, verifier or software. It says automated tools, even well configured, can't entirely verify access control or business logic, and that application-specific verifications, like the unit and integration tests an organisation already writes, can cover what tools can't. It strongly encourages documentation- or source-led (hybrid) penetration testing, which many requirements will need. It treats documented security decisions as the organisation's, not the developer's. And it insists that "testable using automation != running an off the shelf tool" (Assessment and Certification). So:

- **needs a third party** marks two groups: the documentation rows (2.1.1, 6.1.1, 8.1.1, 15.1.1), whose decisions belong to the organisation; and the rows that live in the deployed environment (12.1.1, 12.2.1, 12.2.2, 13.4.1), which v0 never reaches (real deploys are out of scope; release is a stub).
- **The access-control and business-logic rows (2.3.1, 8.2.1, 8.2.2, 8.3.1) are asserted.** ASVS names application-specific tests as a way to verify them and asks for no independent party, so the builder can cover them; in the factory, only instructions and a one-trial review catch do.
- **demonstrated** needs a deterministic gate to catch the requirement's bad case on a fixture or test, across what the requirement covers. A catch by model review alone is named in the Note, but the row stays asserted: the factory files what a model says as asserted (DESIGN principle 1), and review fixtures run one trial per grounding (pass^k is not built, DESIGN "Next" item 6).
- **Partial coverage takes the lower status** (BRIEF: when in doubt, choose the lower). The Note says which part is demonstrated.
- `gate:sast` also runs the configured registry ruleset (`p/default` by default) on the files each change touches. Nothing shows what it covers (the fixtures README records `--config auto` missing fixture 08), so it lifts no row above gap on its own.

## What the factory does for product security, in brief

- **Review focus by risk class** (`factory/stages/triage.py`, `REVIEW_FOCUS`). Class `auth` names ASVS V6, V7 and V8, plus V3.3 and V3.5 where a session lives in a cookie (V9 and V10 where tokens or OAuth are involved). `personal-data` names V14 and V8; `money` names V2. A class is added only when the story or acceptance uses one of its words, or the diff touches one of its paths. Below, "Auth focus" means this text in `risk.json`, which reaches both reviewers.
- **Reviewer brief** (`factory/prompts/reviewer.md`). On every change it asks for missing authentication or authorisation checks, data shown to the wrong user, injection, secrets in code or logs, and removed validation.
- **Spec brief** (`factory/prompts/spec.md`). It asks for criteria that cover bad input, a missing record and a caller without permission. The tests written from them are locked before the build, and `gate:tests` runs them on every later change.
- **Axis rows in the review packet.** With `grounding: seeds` (the default), only P2.1 (auth: apply the matching ASVS chapters at the level the client's data warrants) and P2.2 (personal data) cite ASVS. With `grounding: distillations`, every packet also carries listener rows that name L1 IDs: L1.35 (6.1.1, 8.1.1), L3.20 (login abuse-case tests), L5.65 (1.2.4, 1.2.5, 1.3.2), L5.67 (13.4.1, 6.3.2), L5.68 (2.2.2, 8.3.1), L5.69 (8.2.2) and L6.59. L2.54 (the V5 file rows) and L2.53 (set the ASVS level) never reach a packet: they are phase-2 rows, and no risk class's terms select them (`factory/axis.py`, `CLASS_TERMS`).
- **Deterministic product checks:** `gate:sast` (semgrep, plus pinned rules for SQL built from strings and for evaluating strings built at run time), `gate:deps` (osv-scanner on the lockfiles the change touches), `gate:secrets` (gitleaks; it bears on L2 rows, not L1), and `gate:tests` / `gate:locked-tests` (the client's own suite, locked).

**Three findings that cut across rows:**

1. **The factory warrants the change, not the application.** Reviewers judge the diff, but ASVS requirements are properties of the whole application. A baseline that already fails an L1 row passes unless a change touches it. The calibration sample app passes every control run, yet its session cookie `sid` (`calibration/sample-app/src/auth/middleware.js`) has neither name prefix (3.3.1), and it has no common-password check (6.2.4).
2. **No ASVS level and no applicability record.** ASVS leaves the level to the organisation, and its verification report should summarise the requirements checked and must note those that don't apply. The factory's config has no level setting, and the pack records neither applicability nor requirement IDs (see Verification obligations, below the table).
3. **Reviewers get chapter names, not requirement text.** Unless grounding is `distillations`, a reviewer checks an L1 row only from its own knowledge of ASVS 5.0.
