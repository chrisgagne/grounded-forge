## How to read this

- **Status** follows the brief. `demonstrated` needs both a ledger event on every change and a named test or calibration fixture that shows the mechanism catching the bad case. I add one rule to keep it strict: a row is `demonstrated` only when the factory covers the task's own sentence, not just a part of it. Where the factory demonstrates part and nothing covers the rest, the row is `asserted` (the lower status), and the Note names the uncovered part. Where the rest is by nature the producer's organisation or environment, the row is `needs a third party`, and the Mechanism and Evidence columns still name what the factory supplies.
- **Evidence** names ledger events as `stage:check` (for example `gate:secrets`, `review:leg:reviewer-claude`, `sign:signature`), tests as `tests/file.py::test_name`, and fixtures as `calibration/defects/NN-name`. Every one was checked to exist at `e8cd00f`; those the resolution added, at `3a4e070`.
- **SSDF examples.** "Example N" means the task's Notional Implementation Example N. The SSDF says no example is required (Section 2, p. 4), so examples never set a status; they show what an uncovered part looks like.
- **SP 800-218A rows.** One row per R, C or N item, using the Profile's own IDs (Section 3, p. 6: "PO.1.2.R1" is the first recommendation for task PO.1.2), plus one row per task or practice the Profile adds ("Not part of SSDF 1.1") or whose text it modifies ("Modified from SSDF 1.1"). Tasks the Profile leaves at "No additions to SSDF 1.1" and does not modify only receive a priority, so they fall outside this table and are assessed at their SSDF 1.1 rows (PO.4.2, PO.5.2, PW.1.2, PW.1.3, PW.4.2, PW.9.1, RV.3.2, RV.3.3, RV.3.4).
- **IDs name their source.** Every row's ID starts with `SSDF 1.1`, `218A` or `CISA`, because the two NIST documents share numbers that don't mean the same thing. SSDF 1.1's PW.3 practice is retired (Table 1, p. 12: "Moved to PW.4"), with its tasks PW.3.1 and PW.3.2 moved elsewhere; 218A reuses PW.3 for a new practice on the integrity of training data, with new tasks PW.3.1–PW.3.3 (p. 14–15). Where 218A modifies a task (PO.1.3, PS.3.2, PW.2.1; for PW.2.1, 1.1's "and/or" becomes "and"), the SSDF 1.1 version and the 218A version are separate rows in separate tables, never one row. A bare cross-reference inside a table means the same document as that table.
- **[S]** marks a 218A row that does not apply because of the Profile's scope: "This Profile’s scope is AI model development, which includes data sourcing for, designing, training, fine-tuning, and evaluating AI models, as well as incorporating and integrating AI models into other software" (Scope, p. 2). Its Audience (p. ii) separates AI model producers from AI system producers. The factory is an AI system producer: it builds hosted Claude and Codex models into its own legs, and it holds no weights, training data or model releases. I keep rows about *testing* data and evaluation where they apply to the factory's calibration of its model reviewers, because "evaluating AI models" is in scope. Rows about the hosted models the factory integrates (their use, versions, provenance and testing) apply too, because "incorporating and integrating AI models into other software" is in scope; [S] stays on rows whose subject the factory doesn't have: weights, model code, training pipelines and data, reward models and model releases.
- **[N]** marks a 218A note. Section 3 (p. 6) defines N items as "additional information besides recommendations and considerations", so they set nothing to meet. They are marked not applicable, with any relevance noted.
- **Subject.** Most SSDF rows are `process` (the factory as the producer's development process). `product` is a requirement on the client's software. `agent` is the factory's own model legs, tools, prompts and permissions.
- **CISA rows.** The form attests the producer's practices. Each row judges the practice the item names, for changes run through the factory. Mechanism says what the factory supplies; Note says what the producer's own organisation must supply. Sub-items 1b(i) and 1b(ii) each carry 1b's lead-in. The form maps item 4 and its sub-items together to one SSDF list (Appendix, p. 10).
- **GitHub:** at the coordinator's request, a Note says "GitHub: <feature>" where a GitHub security feature would close a row or raise its status. Statuses don't count those features: the factory doesn't use them, and nothing is pushed to GitHub.
- **PROPOSED** marks any threshold, value or design the standard does not itself supply.
