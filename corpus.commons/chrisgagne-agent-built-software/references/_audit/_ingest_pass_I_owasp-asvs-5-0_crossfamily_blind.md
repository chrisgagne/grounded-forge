## 2. Numbered findings

1. **Deep line 41 — quotation exactness.**  
   The quotation changes the source’s double quotation marks around `"fail"` and `"pass"` to single quotation marks. Tape line **122** contains double quotation marks. The automated checker permits this nesting convention, but the brief’s stricter character-exact rule permits only smart-quote normalisation.

   **Exact fix:** replace the quoted span with:
   > “the verification must result in a "fail" or "pass" decision” [V]

2. **Deep line 168 — changed requirement: what must be per-response.**  
   “Per-response nonces or hashes at L3” attaches *per-response* to the nonces or hashes. Tape line **664**, requirement **3.4.3**, requires a **per-response policy** using nonces or hashes. It does not independently require each hash to change per response.

   **Exact fix:** replace:
   > and per-response nonces or hashes at L3

   with:
   > and a per-response policy using nonces or hashes at L3

3. **Deep line 171 — dropped scope qualifier.**  
   “Automatic redirects to other domains only to allowlisted destinations” omits the restriction to destinations **not controlled by the application**. Tape line **705**, requirement **3.7.2**, includes that qualification.

   **Exact fix:** replace the summary of 3.7.2 with:
   > automatic redirects to a different hostname or domain not controlled by the application only when the destination is allowlisted (3.7.2)

4. **Deep line 178 — broadened requirement scope.**  
   “No CR or LF in HTTP/2 or HTTP/3 header fields” presents an unrestricted prohibition. Tape line **755**, requirement **4.2.4**, concerns **accepting HTTP/2 and HTTP/3 requests**, including their header fields and values.

   **Exact fix:** replace that clause with:
   > acceptance only of HTTP/2 and HTTP/3 requests whose header fields and values contain no CR, LF or CRLF sequences (4.2.4)

5. **Deep line 188 — dropped file-origin and execution-context qualifiers.**  
   “Files in public folders not executed as server-side code” extends requirement **5.3.1** to all files in public folders. Tape line **825** specifies files **uploaded or generated by untrusted input**, and execution **when accessed directly with an HTTP request**.

   **Exact fix:** replace that clause with:
   > files uploaded or generated by untrusted input and stored in a public folder not executed as server-side program code when accessed directly through HTTP (5.3.1)

6. **Deep line 188 — weakened requirement through omitted sanitisation.**  
   “Strictly validated user filenames” presents validation alone as the alternative to internally generated or trusted path data. Tape line **826**, requirement **5.3.2**, requires **strict validation and sanitisation** when user-submitted filenames or metadata must be used.

   **Exact fix:** replace the summary of 5.3.2 with:
   > file paths built from internally generated or trusted data, or, where user-submitted filenames or file metadata must be used, subjected to strict validation and sanitisation, against path traversal, LFI, RFI and SSRF (5.3.2)

7. **Deep line 199 — changed object of random generation.**  
   After introducing lookup secrets, TOTPs and out-of-band mechanisms, “generated by a CSPRNG (6.5.3)” leaves the statement applying to TOTPs themselves. Tape line **955** specifically identifies **time-based one-time password seeds**, alongside lookup secrets and out-of-band authentication codes.

   **Exact fix:** replace:
   > generated by a CSPRNG (6.5.3)

   with:
   > lookup secrets, out-of-band authentication codes and TOTP seeds generated by a CSPRNG (6.5.3)

8. **Deep lines 221 and 395 — broadened opposition to client-side authorisation.**  
   Line 221 says enforcement is “not in client-side code”; line 395 categorically rejects client-side authorisation as a security control. Tape line **1152**, requirement **8.3.1**, rejects controls **an untrusted consumer could manipulate**, rather than every possible client-side enforcement point. The glossary explicitly includes a trusted API on a securely booted client device as a possible Trusted Service Layer, tape line **2023**.

   **Exact fixes:**

   At line 221, replace the 8.3.1 clause with:
   > enforcement at a trusted service layer, without relying on controls an untrusted consumer could manipulate, such as client-side JavaScript (8.3.1, L1)

   Replace line 395 with:
   > - *Client-side input validation and consumer-manipulable authorisation controls.* Client-side validation must not be relied upon as a security control; authorisation must be enforced at a trusted service layer without relying on controls an untrusted consumer could manipulate (V2, 2.2.2; V8, 8.3.1).

9. **Deep line 238 — dropped applicability condition.**  
   “PKCE required, with 'plain' rejected (10.4.6)” omits **if the code grant is used**. Tape line **1308** makes that condition explicit.

   **Exact fix:** replace that clause with:
   > if the code grant is used, PKCE required, with 'plain' rejected (10.4.6)

10. **Deep line 249 — reversed nonce/IV restriction.**  
    “Nonces and IVs never reused for one key and data element” reverses the relationship in requirement **11.3.4**. Tape line **1442** says these values must not be used for **more than one encryption-key/data-element pair**.

    **Exact fix:** replace that clause with:
    > nonces, IVs and other single-use numbers not used for more than one encryption-key/data-element pair, with generation appropriate to the algorithm (11.3.4, L3)

11. **Deep line 416 — inaccurate audit-status cross-reference.**  
    “See the stamp on line 2” points to a blank line in the frozen reference. No Pass I stamp appears there. This is an internal provenance defect; there is no supporting tape passage.

    **Exact fix:** **strip** line 416. An audit-status statement should be added only after the actual audit log and stamp exist.
