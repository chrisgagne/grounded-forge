# K04B-1

Our developers call a ticket finished when the code compiles on their laptop, then testers find it's half-baked. What should a group agree on so "finished" means one thing?

To resolve the issue of developers marking tickets as complete as soon as code compiles, the team needs to establish a shared, explicit Definition of Done (DoD)[1:ALT:open-practice-library][2:IN:scrum-guide-2020]. A Definition of Done is a collaboratively created set of quality standards and criteria that every work item must satisfy before it can be considered complete[1:ALT:open-practice-library].
Key Criteria the Group Should Agree On
Story-Level Acceptance Criteria: Beyond code compilation, each ticket must fulfill explicit conditions of satisfaction (often written using Given/When/Then scenarios) agreed upon during refinement or planning[3:ALT:open-practice-library][4:ALT:open-practice-library][5:ALT:letaw-handbook-sweng-methods]. A user story is only complete when all of its acceptance criteria pass[5:ALT:letaw-handbook-sweng-methods][6:ALT:letaw-handbook-sweng-methods].
Automated Testing & Quality Gates: Incorporate mandatory testing practices into the checklist—such as writing and passing unit tests, integration tests, or automated regression suites[7:ALT:open-practice-library][8:OTHER:approach-perfect-field-guide-scrum-events]. Passing these "quality gates" prevents half-baked code from advancing downstream[9:ALT:open-practice-library].
Peer Review & Code Verification: Require a peer review or peer check where another developer inspects the code for quality, architecture standards, and maintainability before handing it off to QA[9:ALT:open-practice-library][10:OTHER:doe-hpi-handbook-vol2].
Non-Functional Requirements: Include standard technical criteria for every ticket, such as performance thresholds, security checks, error logging, and updated technical documentation[1:ALT:open-practice-library][11:ALT:letaw-handbook-sweng-methods].
Environment & Releasability: Mandate that code must be deployed and smoke-tested in a shared staging/test environment—not just run locally on a developer's laptop—so it forms a usable, potentially releasable product increment[8:OTHER:approach-perfect-field-guide-scrum-events][12:OTHER:approach-perfect-field-guide-scrum-events][13:OUT:scrum-guide-2020][14:IN:scrum-guide-2020].
How to Implement and Enforce the Agreement
Build Consensus Collaboratively: Facilitate a team session (such as a Sprint Retrospective) where developers, testers, and product leaders define the DoD together[1:ALT:open-practice-library][15:OTHER:approach-perfect-field-guide-scrum-events]. If the organization has baseline quality standards, the team's DoD must meet or exceed those requirements[16:IN:scrum-guide-2020].
Make Process Policies Explicit: Publish the agreed DoD criteria prominently (e.g., on your task management board or team wiki) so process policies are transparent to all team members[17:ALT:open-practice-library][18:OUT:scrum-guide-2020].
Foster Peer Accountability: Shift responsibility so that developers themselves are accountable for instilling quality and adhering to the Definition of Done on every ticket, rather than relying on testers to catch incomplete work[14:IN:scrum-guide-2020][19:OUT:scrum-guide-2020].
