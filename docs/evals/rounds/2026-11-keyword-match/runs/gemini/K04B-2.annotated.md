# K04B-2

Our developers call a ticket finished when the code compiles on their laptop, then testers find it's half-baked. What should a group agree on so "finished" means one thing?

To eliminate ambiguity between developers and testers, your team needs to establish a shared Definition of Done (DoD)[1:ALT:open-practice-library][2:IN:scrum-guide-2020]. Code compiling on a developer's laptop only checks basic syntactic validity locally; it does not guarantee that functionality, integration, testing, or user expectations have been met[1:ALT:open-practice-library][3:ALT:open-practice-library].
A Definition of Done is a formal, transparent agreement co-created by the entire team (developers, QA testers, and product owners) that lays out the explicit quality gates every ticket must pass before it can be considered complete[1:ALT:open-practice-library][2:IN:scrum-guide-2020][4:OUT:scrum-guide-2020]. If a ticket does not satisfy every item in the DoD, it cannot be called finished, showcased, or released[2:IN:scrum-guide-2020].
Essential Quality Criteria for a Definition of Done
To ensure "finished" has a single, unambiguous meaning across your group, agree on the following standard requirements:
Satisfied Acceptance Criteria: The ticket fulfills all specific conditions of satisfaction defined for that work item (often expressed in Given/When/Then testable scenarios)[5:ALT:open-practice-library][6:ALT:open-practice-library][7:ALT:letaw-handbook-sweng-methods].
Peer Code Review: Someone other than the code's author has inspected the code for readability, design quality, security vulnerabilities, and adherence to team style guides[8:ALT:open-practice-library][9:ALT:open-practice-library].
Automated & Integration Testing: Code passes all automated unit tests, static code analysis, and integration tests after being merged into the shared repository and deployed to a staging environment—confirming it works beyond the developer's laptop[3:ALT:open-practice-library][10:ALT:open-practice-library][11:OTHER:nist-ssdf-1-1].
Non-Functional & Security Checks: Essential non-functional requirements (such as performance benchmarks, logging, system security checks, and updated documentation) have been satisfied[8:ALT:open-practice-library][12:ALT:open-practice-library][13:OTHER:nist-ssdf-1-1].
No Regression / Defect-Free: Verification confirms that the new code does not break existing application behavior[10:ALT:open-practice-library][14:OUT:scrum-guide-2020].
Complementary Practices to Prevent "Half-Baked" Work
Establish a Definition of Ready (DoR): Set clear entry criteria before developers pick up a ticket (e.g., following the INVEST model) so scope, acceptance criteria, and technical constraints are clear up front[15:ALT:open-practice-library][16:ALT:letaw-handbook-sweng-methods].
Refine the DoD in Retrospectives: Whenever testers discover unhandled edge cases or missing verification steps, use your Sprint Retrospectives to update the Definition of Done so the team continuously tightens its quality standards[17:OTHER:approach-perfect-field-guide-scrum-events][18:OUT:scrum-guide-2020].
