What you're describing is the problem a **Definition of Done** (DoD) is meant to fix. Right now each developer applies a private test ("it compiles for me"), and testers find out later that their own test was different. The corpus says the group should agree on these things:

**1. One written standard that applies to every item, not a private judgement.**
The Scrum Guide calls the Definition of Done "a formal description of the state of the Increment when it meets the quality measures required for the product." It says the DoD exists to give "everyone a shared understanding of what work was completed." The Open Practice Library (OPL) describes it as criteria the team agrees, shares with others, and meets before *any* team member treats a work item as complete.

**2. Include quality work as well as feature work.**
The OPL says a DoD is where the team manages the "non-functional and functional work that should be performed for each and every work item." Its examples are quality, assurance and documentation activities, done throughout delivery. This targets your problem directly: "compiles on my laptop" only checks part of the functional work and none of the rest.

**3. Treat it as a gate.**
In the Scrum Guide, an item that doesn't meet the DoD "cannot be released or even presented at the Sprint Review." It goes back to the backlog. Without this rule a DoD is just a wish list. "Mostly done" doesn't count as done.

**4. The people bound by it write it together.**
The OPL calls it "Collaboratively created, maintained and enforced criteria by the team". It suggests a 15-minute session where one person writes from everyone's input, with a quick consensus check such as roman voting. Your testers should be in that session, since their idea of "done" is the one being missed today. The Scrum Guide adds two rules that matter if you have several teams:
- If the organisation already has a DoD, it's the minimum and teams can only add to it.
- Teams working on the same product "must mutually define and comply with the same Definition of Done."

**5. Use it when planning.**
In the Scrum Guide, developers plan each item as the work needed to meet the DoD. They also forecast more confidently when they know their DoD. Testing, review and documentation then get estimated up front, so they aren't discovered at the end.

**6. Review it regularly.**
The Scrum Guide lists the DoD among the things the team inspects at every retrospective. When testers keep finding the same kind of gap, that's a reason to add a line to the DoD.

**One distinction to settle.** Sources use "done" in two different ways:
- **Letaw's software engineering handbook** treats it per story: what counts as done is "negotiated with the client and added to the user story as acceptance criteria," written in given-when-then form.
- **The Scrum Guide and the OPL** treat the DoD as one quality standard for *every* item. The OPL keeps it separate from each story's own conditions of satisfaction.

You probably need both: a team-wide DoD (tested, reviewed, documented, and so on) plus acceptance criteria for each ticket. Name them separately so nobody thinks meeting one means meeting the other. The OPL also suggests a **Definition of Ready**, meaning criteria a ticket must meet before anyone starts it. That helps if half-baked tickets also start out half-specified.

**A starting point (my own example, not from the corpus):** code reviewed by someone else; merged to the main branch; automated tests written and passing; deployed to a shared test environment, not just a laptop; acceptance criteria shown to a tester; documentation updated. Cut or add lines in your team session. What matters is that the team writes the list and enforces it as a gate.

**Gaps:** None of these sources gives a standard software DoD checklist, so the example list is unsourced. The Open Kanban material didn't cover making done-criteria explicit.
